# Day 5: Automated Evaluation - Golden Sets, Retrieval Metrics, Regression Tests

## 1. Objective
Stop eyeballing individual answers and start measuring the system: a golden question set with known-correct
pages, retrieval metrics (hit@k, MRR, recall@k), an answer-correctness check based on citations (not vibes), an
optional LLM-judge score, and `scripts/run_eval.py` - the tool you re-run after every future change to see
whether it helped or hurt.

## 2. Why this matters
Every day so far made a judgment call with a plausible-sounding justification: chunk size 350 tokens, rerank
threshold 4.0, RRF k=60. None of those were *measured* - they were reasonable defaults. Production AI engineering
means replacing "reasonable default" with "measured against a golden set" wherever it matters. Today builds the
tool that makes that possible; Day 6+ will use it to actually tune those defaults.

## 3. Theory
**Golden dataset.** A set of questions with KNOWN correct answers (here: known correct page numbers), built by a
human who understands the document - not generated by an LLM guessing what might be asked. Critically, it must
include questions the system should REFUSE (`expected_pages: []`): most tutorials only test "can it find the
right answer" and skip "does it know when to say no", which is usually the more expensive failure in production
(a confident wrong answer costs more trust than an honest refusal).

**hit@k, MRR, recall@k.** See `app/eval/retrieval_metrics.py` docstring for full definitions. Short version: hit@k
is a pass/fail per question ("was the answer somewhere in the top k"), MRR rewards finding it EARLY (rank 1 scores
1.0, rank 10 scores 0.1), recall@k matters when an answer spans multiple pages. Use hit@3 as your headline metric,
MRR to catch retrieval that "eventually" works but ranks poorly.

**Answer correctness via citations, not text similarity.** Comparing generated text to a reference answer with
string similarity is unreliable (many correct phrasings, one wrong number). Instead: did the answer cite the
PAGE that actually supports it? This reuses Day 4's citation validation - a second dividend from building
citations properly the first time.

**False refusal vs hallucinated citation - two distinct failure modes.** A system that refuses everything scores
0% hallucination and 100% false refusal; a system that always answers scores the opposite. Both numbers are
reported separately so tuning one doesn't silently break the other (this is exactly why `min_rerank_score` needs
a measured value, not a guess - Day 5 builds the ruler, Day 6+ does the measuring).

**LLM-as-judge (optional, soft signal).** An LLM scores 0-10 whether the answer text actually addresses the
question well, given reference keywords. This is NEVER the source of truth for pass/fail (that's the deterministic
citation check) - it's a secondary quality signal, and it costs real tokens, so it's the first thing to skip when
minimizing spend (`--no-judge`). Full frameworks like RAGAS/DeepEval formalize this further (faithfulness,
answer relevancy, context precision) - flagged here as the natural upgrade, not built today, to keep today's scope
honest about what a from-scratch judge does and doesn't cover.

**Why the runner takes plain callables, not FastAPI dependencies.** `run_eval(golden, document_id, search_fn,
ask_fn, ...)` never imports FastAPI. The regression tests inject deterministic fakes; `run_eval.py` and
`verify_day5.py` inject the real pipeline. Same pattern as `Embedder`/`Reranker`/`Generator` Protocols throughout
this project - testability comes from depending on a narrow interface, not a framework.

## 4. Architecture
```
evals/golden/*.json  (your questions + known correct pages, incl. some intentionally unanswerable)
        |
        v
scripts/run_eval.py --pdf your.pdf --golden evals/golden/your_set.json
        |
        v
  for each question:
    search_fn -> hybrid search -> ranked page numbers  -> retrieval metrics (hit@k, MRR, recall@k)
    ask_fn    -> full /ask pipeline (rerank+generate)  -> AskLikeResult (refused?, cited pages, answer text)
      -> check_citation_correct, check_keyword_hit, judge_correctness  -> per-question is_correct
    [optional] judge_fn -> LLM 0-10 quality score (only for answered, non-refused questions)
        |
        v
  EvalReport: aggregate hit@k/MRR/recall, answer_accuracy, false_refusal_rate,
              hallucinated_citation_rate, avg_judge_score, cost, per-question detail
        |
        v
  printed table + evals/reports/<timestamp>.json
```

## 6-7. Code notes
- `retrieval_metrics.py` / `answer_metrics.py`: pure functions, zero I/O - the easiest code in the whole project
  to unit test exhaustively, which is why they have the most edge-case tests per line of any module so far.
- `runner.py`: `_Row` pairs each `GoldenQuestion` with its computed `QuestionReport` so aggregation (false refusal
  rate, hallucination rate) can check `golden.is_unanswerable` directly, rather than trying to infer intent from
  the result after the fact - a design correction made while building today (an earlier draft tried to infer
  answerability from result signals, which was fragile; keeping the golden question alongside its result was the
  fix - documented here because that reasoning is worth remembering next time this file changes).
- `run_eval.py`: wires the SAME `run_eval()` used in tests to the real `SearchService` and `answer_question()` -
  proof that the Protocol-based design pays off: no eval-specific pipeline code exists.
- `judge.py`: mirrors `reranker.py`'s structure (`JsonLLM` + JSON-schema call + clamped score) - same pattern,
  different prompt, reused review skill.

## 9. Testing
131 tests total (32 new), zero live LLM calls: retrieval metrics (9 cases), answer metrics (10 cases incl. all
four correctness branches), loader (7 cases incl. malformed/duplicate/empty), runner integration (aggregation
across 7 synthetic scenarios covering every metric), judge (parsing/clamping/malformed-reply). `verify_day5.py`
adds a live run against a real 8-question + 1-unanswerable set with pass/fail thresholds.

## 10. Failure cases
Malformed golden JSON: clear `GoldenSetError` naming the file and problem, not a stack trace. Duplicate question
ids: rejected at load time (silent overwrites would corrupt aggregation). Judge returns unparseable JSON: scores
0, doesn't crash the run. Zero answerable questions in a set: false-refusal/hallucination rates default to 0.0
rather than dividing by zero.

## 11. Security
Golden set files are local, developer-authored JSON - no special handling needed. `run_eval.py` costs real money
per run; consider it a manual/CI-gated tool, not something exposed as an API endpoint.

## 12. Observability
Every `EvalReport` records `cost_usd` and `duration_ms` for the whole run, plus a full per-question breakdown
saved to `evals/reports/<timestamp>.json` - a history you can diff across days to see whether a change actually
helped (Day 11: CI/CD will eventually gate merges on exactly these reports).

## 13. Cost
Retrieval-only checks (`--no-rerank --no-judge`... actually retrieval metrics never call the LLM at all) are
nearly free (query embeddings only). A full run with rerank + generation + judge on 9 questions is on the order
of a few cents. `--no-judge` and `--no-rerank` are there specifically to cut cost when iterating quickly.

## 14. Production improvements
Integrate RAGAS or DeepEval for faithfulness/context-precision/answer-relevancy metrics beyond citation-page
matching; store eval history in a database instead of flat JSON files for trend dashboards; gate CI on a minimum
hit@3 and a maximum false-refusal rate (Day 11); expand the golden set as real user questions come in (the best
golden sets are grown from production traffic, not invented upfront).

## 15. Interview Q&A
- *How do you evaluate a RAG system?* A golden set of questions with known-correct source locations, split into
  retrieval metrics (hit@k, MRR) and answer metrics (citation correctness, refusal correctness) - never just
  "does the answer look right", because that doesn't scale or catch regressions.
- *Why include unanswerable questions in your eval set?* Because a system that never refuses looks great on
  answerable questions and terrible in production the first time it confidently invents an answer; you have to
  measure both directions of error.
- *What's the difference between hit@k and MRR?* hit@k is binary per question; MRR is continuous and rewards
  ranking the right answer FIRST, not just somewhere in the top k - useful for comparing two "equally successful"
  retrieval configs.
- *Why citations for answer correctness instead of comparing to a reference answer?* Text similarity is fragile
  (many valid phrasings); a citation to the right page is a structural, verifiable fact that reuses the grounding
  work already required for trust.
- *Why is LLM-as-judge a secondary signal, not the pass/fail criterion?* It's an opinion from another model, not
  a verifiable fact - useful for catching quality issues a citation check can't see, but not something to gate
  correctness on alone.
